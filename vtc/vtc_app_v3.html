What video codec should I use?

The only choice that meaningfully changes file size. Every codec trades off size, quality and speed — older ones are worse at all three. For a given quality the codec doesn't change how it looks, only how big the file is and how long it takes to make. If your machine has a hardware encoder for a codec, it will be considerably faster than choosing a codec without hardware encoding.

Very Thoughtful Compression

Very Thoughtful Compression evaluates files in a video library according to the quality and device compatibility you want.

It evaluates every file individually to make lossless changes that improve compatibility and/or to re-encode the files that are genuinely too big given your quality requirements. It leaves everything that is at, or below your quality target exactly as it is to avoid needless degradation.

Most batch re-encoders don't work this way. They apply one setting to every file, or aim at a relative target like "70% of the current bitrate". If you do this repeatedly, the same movie is ground down run after run (3.5 GB → 2.2 GB → 1.2 GB etc), bleeding a generation of quality each time. A library isn't uniform: some files were encoded with generous headroom, others were squeezed dry years ago. Re-encoding the second kind buys almost nothing and costs quality that never comes back.

VTC measures before it touches anything. Each file's real density is read — bits per pixel per frame, from its bitrate, resolution and frame rate. Your desired Quality Tier is a bpp too — a density, not a bitrate — so the target for this file is tier bpp × its pixels × its frame rate × the codec factor. No resolution rules anywhere.

Because that target is absolute — a function of the tier you choose and the file's own pixels and fps, never a fraction of its current size — it converges: one encode lands a file at the tier, and every run after that sees it already there and leaves it alone.

A file is only re-encoded when it's more than 10% over its target; at or under, it is left exactly as it is. Modern codecs (H.265, AV1, VP9) are never transcoded — that usually spends a generation of quality to save very little. Targets are floored and never set above the source, so a file is only ever shrunk, never inflated.

Before encoding, the expected output is modelled: if it won't clear your saving threshold, the encode never starts. Afterwards the source is replaced only if the new file exists, is non-empty, ffprobes as a valid video, and actually beat the threshold. If not, the original stays and we report what happened in the run report.

Nothing is ever silently lost — dropped subtitle tracks archive the original even on delete, and every outcome is named in the report.

A stopped run picks up where it left off. Every file that reaches a decision is recorded in a resume ledger at the scan root, tagged with a signature of the settings that produced it. Re-run a processed file and it will be skipped — the absolute target has been reached and the ledger check both prevent that happening.

Quality is part objective, part perceptual. There is measurably more information in a higher-quality file — but exactly what you call that, or how much difference still counts as "the same", is a judgement. Codecs are good at some material and less good at others: grainy sources need more space to encode all that detail, so a tier up can be worth it there. Software encoders (libx264/libx265) are more nuanced — better quality for the same bitrate — while hardware encoders (VideoToolbox) are much, much faster. How much speed is worth trading for how much quality is a call only you can make. We've set Excellent at roughly a streaming platform's 1080p release and banded OK, Good, Stellar and Insane around it the same way — but your eye might land differently, so every tier's density is yours to change in Advanced settings → Quality tiers.

A codec is not a container. The container is the wrapper. It holds the video track, one or more audio tracks, any subtitle tracks, plus chapters and metadata, and keeps them in sync — but it does not decide how big the file is or how good it looks. The codec inside it does that. The same H.264 video is exactly the same size in an MP4 as in an MKV. Rips are often large because they carry high-bitrate video and lossless audio, not because of the wrapper.

What differs between containers is what they can hold and what will play them.

  • MP4 is the universal standard — it plays on essentially everything, but only carries a limited set of audio codecs and can't hold image-based subtitles.
  • MKV holds almost anything — any codec, unlimited tracks, image subtitles — but far fewer devices play it directly.
  • Other containers are more specialised or older (see the table).

Whatever the source, VTC delivers your preferred container (MP4 by default): a lossless remux where the codec allows, a transcode where it doesn't (old wrappers like AVI and WMV). On Auto it uses MP4 and falls back to MKV only when MP4 would lose something.

Video codecs

VTC outputs H.264 or H.265; what it does with a source depends on how modern that codec already is.

  • H.264 / AVC (2003) — the universal baseline, plays on virtually anything, but ~2× the size of H.265.
  • H.265 / HEVC (2013) — H.264 quality in 40–55% of the space (~60% smaller at 4K); plays on most things since ~2015, bar some smart TVs and Firefox browser. This is VTC's default output but worth considering H.264 if you are streaming to a wide variety of devices.
  • AV1 (2018) — likely the future (saves ~30% more space than H.265), royalty-free, but slow to encode and still growing in support. Already modern, so VTC leaves it alone; not currently an output option.
  • VP9 (2013) — Google's codec, roughly H.265-efficient, common on YouTube and WebM. Modern: left alone, not currently an output option.
  • Legacy — MPEG-2, VC-1, Xvid/DivX, WMV — old and inefficient (2–4× H.264). VTC rescues these: transcoded to your chosen modern codec near their original bitrate, so quality holds while the file shrinks, usually dramatically.
Audio MP4 can't hold

Audio is passed through with no quality loss, but there are some cases where that isn't possible in an MP4. An MP4 carries only AAC, AC-3 (Dolby Digital) and E-AC-3 (Dolby Digital Plus). Blu-ray rips often use formats MP4 doesn't support, so you can either convert them to an excellent but lossy alternative (AAC — the channel layout is kept, so a 7.1 track stays 7.1) or keep them as-is by using the MKV format and accept any device-compatibility problems. What each conversion costs:

  • DTS / DTS-HD MA — DTS is lossy (like AC-3); DTS-HD Master Audio is lossless. Converting to AAC discards the DTS decode path; from DTS-HD MA you also lose the lossless master.
  • Dolby TrueHD (often with Atmos) — a lossless Dolby master. Atmos height data rides on the TrueHD/E-AC-3 stream; plain AAC drops the object-based Atmos layer and the lossless quality.
  • LPCM / raw PCM — uncompressed. Re-encoding to AAC is a big size saving for a small, usually inaudible cost.

A single film often carries several subtitle tracks, in different languages and of different kinds. VTC keeps exactly the ones you ask for — by kind and by language — and never destroys a track silently.

Kinds

Normal — the complete dialogue: everything that is said. Forced — only what a native speaker still needs: translated on-screen text and signs, and lines spoken in another language (the alien speaking in a subtitled scene). HoH / SDH (Hard of Hearing / Subtitles for the Deaf and Hard of hearing) — a full transcript that also describes sound, [door slams], [ominous music], and names who is speaking. In Subtitles you tick any combination of kinds and list the languages to keep; VTC filters every file to just those.

Text vs image subtitles

Text subtitles are just words with timings — SRT, ASS/SSA, WebVTT. They're tiny, searchable, and can be restyled by the player. Image subtitles are actually little pictures of each line — PGS from Blu-ray and VobSub from DVD — burned as bitmaps because the disc used a specific font. They look exactly as authored, but can't be searched, restyled, or turned into text without OCR.

Embedded vs sidecar (.srt)

Embedded means the subtitle lives inside the video file as its own track — one file, nothing to misplace. A sidecar is a separate .srt file sitting next to the video with the same name (Movie.srt), which Plex, VLC, Infuse and Kodi pick up automatically. A .srt is plain text, so it's lossless and it plays even more widely than an embedded track.

What VTC does. Text tracks are embedded into MP4 (as mov_text), all of them. In the rare case one can't embed, it's written to a sidecar .srt instead — lossless, and the default on Auto because it plays more widely than forcing the file to MKV. Image tracks (PGS/VobSub) can't live in an MP4 at all and can't become .srt without OCR, so keeping them means keeping the file as MKV (Auto does this); if you've chosen to drop them, the original is archived rather than deleted always. The report sorts every file into three outcomes — Thoughtfully processed, Left alone, and Needs a look — each a tab you can open. Click any row to reveal that file in your file browser; Save log… saves the full log to disk.

Thoughtfully processed

The file was rewritten — smaller, or the same size but rehomed into a more compatible container. The detail line leads with the container change, then the video and audio:

  • Shrunk — re-encoded to your tier because it was more than 10% over. The one lossy operation.
  • Transcoded — a legacy codec (Xvid, MPEG-2…) rescued to a modern one at full fidelity.
  • Remuxed / copied — a lossless container change (mkv→mp4). Video and audio are copied byte-for-byte; nothing is re-encoded.
Left alone

Nothing was written; the original is untouched. The row says which of these it was:

  • Already efficient — within reach of your tier's density, so re-encoding would spend quality to save almost nothing. This also covers a file an earlier run under the same settings recorded as done and which hasn't changed since (matched on path, size and timestamp), so a repeat run skips it without re-probing.
  • Below your quality tier — the source is lower quality than the tier you chose. It's left as-is because VTC never inflates a file (you can't add detail that isn't there) — worth knowing if you'd rather re-source it at higher quality.
  • Already modern — H.265, AV1 or VP9, which are never transcoded.
  • Already converted — the output for this file already exists from a previous run.
  • Saving too small — the encode was tried or modelled and wouldn't clear your saving threshold, so the original was kept.
  • Codec kept — a legacy codec you chose not to transcode (Format & container → "only if lossless").
  • Left as-is — a non-MP4 file your Format & container choice said to leave untouched.
  • Already encoded by this tool — a file VTC itself produced; re-encoding it would cost a second generation of quality, probably for nothing.
Needs a look

Worth a human glance — each marked with an orange ✱ at the start of the name. Nothing here was changed; these are files VTC couldn't safely handle:

  • Couldn't read file — ffprobe couldn't parse it. Since ffmpeg reads almost every format, this usually means the file is corrupt or truncated, not exotic. Reveal it and try to play it.
  • Error — the encode failed. The row shows a short reason; the full text is in the saved log (long errors end in "… see log"). The original is untouched.
  • Warning — the file was handled, but with a caveat worth knowing (for example a subtitle written to a sidecar .srt).
Retry in software

Hardware encoders are fast but occasionally choke on the odd file. When a run leaves errors, a Retry N in software button appears below the report (it names the file when there's one). It re-runs just those files with the slower libx264/libx265 encoder, which is more forgiving and slightly better per bit. The results replace that file's row.

"Same size" is not a bug

A remux (mkv→mp4) or an already-lean file reads as "7 GB → 7 GB": the wrapper, or nothing, changed — on purpose. The detail line says which. And because the target is an absolute density, one encode lands a file at your tier and every run after leaves it alone; a lossless remux never counts as a re-encode, so a remuxed file stays eligible for a real shrink later.

A codec-aware re-encoder for large video libraries. It measures every file first — bits per pixel per frame — and only re-encodes the ones actually over your chosen quality tier, so already-lean files are left untouched and repeated runs converge instead of grinding files smaller. Modern codecs are never needlessly re-encoded; MP4-incompatible legacy formats are rescued at full fidelity; subtitles are never silently destroyed.
